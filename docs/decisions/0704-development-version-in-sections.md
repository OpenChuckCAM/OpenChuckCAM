## Context

The owner asked on 27 Nov 2026 for the changes in the *Development version* of `user-docs/src/release-notes.md` to be grouped into sections, so that users can see at a glance what interests them, suggesting "UI and workflow", "Operations and strategies", "Simulation", "G-code generation" and others that fit.

On `main` at `bfbcac7` the section held 47 bullets in one flat list, in the order the pull requests merged: keyboard and dialog changes between ramp and face flow changes, one post template change between two tool changes. The nightly pre-release page showed the same list. Every open pull request adds one bullet there, so the sooner the sections exist, the fewer bullets need moving.

## Decision

1. **Eight sections, in this order** (the program's own steps), as `### ` headings inside `## Development version`:
   1. *UI and workflow*: windows, the start page, the keyboard, dialogs, the view and what it shows, the project panel, Results and the wording of messages, projects and their recovery.
   2. *Models, setups and workholding*: import, stock, held regions, tabs and machine profiles.
   3. *Tools and tool libraries*.
   4. *Operations and strategies*: each operation's settings, notes and warnings, its Geometry section and its labels in the view.
   5. *Simulation*: the stock simulation, deviation, tool load and the checks the simulation makes.
   6. *G-code generation and posts*: Post and export, the built-in posts and your own, post templates and the checks on the written program.
   7. *Command line*: `openchuck-cli`.
   8. *User guide and examples*: the guide, the example projects, the downloads and the nightly pre-release page.

   The names and their order are one list in xtask (`SECTIONS` in `xtask/src/changelog.rs`) and its copy in the guide's build (`SECTIONS` in `user-docs/tools/build.py`, item 7), which an xtask test compares with it; a rename is a change to both lists, the page and the rule text.
2. **One bullet, one section.** A change goes in the section where users meet it, never in two: a new setting of one operation, with its note, goes in *Operations and strategies* although it shows in a panel; a change to every dialog or to all messages goes in *UI and workflow*; a warning that the simulation raises goes in *Simulation*; a change to the command line alone goes in *Command line*, and a change seen in both the window and the command line goes in the window's section. A bullet that covers two unrelated changes is split.
3. **Fixes are tagged, not sub-headed, and grouped when shown.** A bug fix's bold lead starts `Fixed:` (as in "**Fixed: the Facing stop marker after generating.**"); a new or changed behaviour has no tag. One rule says what a fix is, in both tools: a bullet whose text starts with `**Fixed:` (in the guide's HTML, `<strong>Fixed:`). In the source, a section's bullets are in merge order (lanes add at the end, so their merges do not reorder each other's bullets); wherever a section is shown (the guide, the nightly notes), its other bullets come first and then its fixes, each group in page order, and `start-release` writes the fixes last in the version's source (item 8). No label is added before the fixes: the `Fixed:` lead, which is kept, is the label. The tag is not checked, because a tool cannot tell a fix from a change, and the check does not enforce any order. Not chosen: *Added*, *Changed* and *Fixed* sub-headings in each section (24 possible headings, and more merge conflicts between lanes).
4. **A heading is there only while its section has bullets.** The first bullet of a section adds its heading, in the order of item 1. An HTML comment at the top of the section lists the sections and the rules of items 2 and 3, and one before the closing reminder says to add a bullet at the end of its section; neither shows in the guide.
5. **The pull request check** (`cargo xtask changelog check-pr`, 0678 item 4) still accepts a bullet in any section as the pull request's entry. It now also fails:
   - a new or changed bullet that is not under one of the eight headings: above the first heading, or under another heading. The message names the bullet and lists the sections in order;
   - a heading of the *Development version* that is not one of the eight, one given twice, one out of order, or one with no bullets, when the pull request brought it (a problem the base already has is not the pull request's).

   These fail whether or not the description says `No user-visible change`, as an internal number does. A bullet the pull request did not touch is still not its problem. The check cannot tell whether a bullet is in the right one of the eight sections: that stays the lane's and the reviewer's judgement.
6. **The sections fold, with their counts, in the nightly notes** (the owner's change). The count is never written in the source: a count kept by hand would change on the same line in every pull request and conflict. Under *What has changed*, each section with bullets is a closed `<details>` whose title is its name and the number of its bullets, `<summary><strong>UI and workflow (13)</strong></summary>`, followed by its bullets (fixes last, item 3); GitHub renders the bullets' Markdown inside it. A section with no bullets is never shown. When the notes are shortened to their limit (0678 item 3), whole bullets are left out from the end, a section with none of its bullets left is left out, and a section's count is of the bullets listed (the closing line already says how many more are in the guide). A bullet above the first heading, which the check of item 5 keeps off `main`, would be listed first, outside any section. `cargo xtask changelog nightly-notes` writes this.
7. **The sections fold, with their counts, in the user guide.** The guide is built by mdBook through `user-docs/tools/build.py`, without the Rust toolchain, so the count is computed there, in Python, by the tooling rule's exception for the user-guide site tools (decision 0678 item 7); no new tool, preprocessor or plugin. After mdBook, on `release-notes.html` only, each `<h3>` whose text is one of the eight names and which is directly followed by a list becomes a closed `<details class="changes">` whose summary is the heading itself, with its count: `<summary><h3 id="ui-and-workflow">UI and workflow (13)</h3></summary>` (the heading keeps its id, so a link to it still works; mdBook's link round the heading text is dropped, because a link in the title would follow the link instead of opening the section). Its list follows, fixes last (item 3); the count is of all its bullets. Every section is closed by default, so the page shows a short list of sections with counts; none is opened by default, the newest included, because the Development version is the only one that changes between builds. Any other heading is left as it is, so the sections of 0.55.0 and 0.55.1 (*Fixed*, *Known limitations*, ...) stay flat, as history, and a future version's change sections, moved there by `start-release`, fold in the same way. `print.html` is not changed, so a printed guide shows every bullet. A few lines in `theme/style.css` show the heading inline beside the marker.
8. **The release moves the sections whole.** `cargo xtask changelog start-release <version>` moves each section with bullets, heading and bullets, in page order, into the new version's draft section, in place of 0678's single *What has changed* list; the version's section then reads summary, the change sections, then the known limitations and issues the writer adds. The *Development version* keeps its introduction, its two comments and the reminder, with no headings. With nothing to move, the draft says "Nothing user-visible has changed since the last release." under *What has changed*, as before. Each section's fixes are written last, each group in page order (item 3), and the draft comment says so. `check-release` is unchanged: it counts the bullets in every section.
9. **The current section is restructured once**, by the mapping under *Verification*; the text of each bullet is unchanged, apart from one bullet split in two (item 2) and the nightly-page bullet, which now says the list is grouped and folds. The sections of 0.55.0 and 0.55.1 stay as written.
10. **Documents.** `AGENTS.md` and `CLAUDE.md` (the changelog rule lines only) say a bullet goes at the end of its section; `docs/releasing.md` gets the list, the order, items 2 to 4, the folding of items 6 and 7 and the move of item 8. The page's introduction says the changes are grouped by what they change.

### The other open pull requests

Each lane merges `main` at its release push (decision 0055) and puts its bullet at the end of its section, as plain Markdown (no count, no `<details>`: those are made when the page and the notes are built). A lane's flat bullet, added after the old last bullet, normally conflicts, because that line moved; the lane takes `main`'s page and adds its one bullet at the end of its section. A merge that goes through cleanly can still leave the bullet at the end of whichever section is last, which the check passes, so the lane looks. The coordinator sends each lane this instruction once this record merges.

## Alternatives considered

- **Sub-headings for *Added*, *Changed* and *Fixed* in each section** (item 3). Not chosen.
- **All eight headings always present, empty ones included.** A lane would never add a heading, but the guide's *latest* release notes would show empty headings. Not chosen; the nightly notes would omit them anyway.
- **A section named in each bullet (a tag such as `[Simulation]`) and grouping only in the generated notes.** No conflicts in the page, but the guide would show the flat list. Not chosen.
- **The count written in the source heading, or the `<details>` written by hand in the page.** Every pull request would change the same line. Not chosen (items 6 and 7).
- **xtask writing the guide's folded page.** One implementation, but the guide's CI action runs without the Rust toolchain and the source would no longer be plain Markdown. Not chosen; the two lists are kept equal by a test (item 1), and the fix rule is one sentence (item 3).
- **The newest section open by default.** Not chosen (item 7).
- **No check of the headings.** Lanes would add a misspelt or new heading unnoticed. Not chosen; the check costs nothing (item 5).

## Consequences

- Every pull request with a *Development version* bullet puts it at the end of its section; Fast checks fail a bullet outside one.
- The nightly pre-release page and the guide's *latest* release notes show the changes grouped, each section folded with its count, fixes last.
- The next release's notes start from the sections.
- Changed files: `xtask/src/changelog.rs`, `xtask/src/changelog/tests.rs` and its two fixtures, `user-docs/tools/build.py`, `user-docs/tools/tests/test_build.py`, `user-docs/theme/style.css`, `user-docs/src/release-notes.md`, `AGENTS.md`, `CLAUDE.md`, `docs/releasing.md`, the record of decision 0678 (a note that this record amends it), the decision index and `docs/open-items.md`. No workflow changes, no new CI job and no runner minutes (the check is the same step of Fast checks).
