# Post definitions

Built-in post definitions as data files, inside the `openchuck-post` crate so the published crate carries them (architecture section 12, decision 0103, GC-03): the Makera Z1 post (GC-09) and the LinuxCNC verification post (GC-10), each with golden tests. They were built in work breakdown slice 6 ([decision 0020](../../../docs/decisions/0020-slice-6-post-and-round-trip.md)) after spikes SP-10 (template engine) and SP-12 (Z1 conventions).

A post is a folder: `post.toml` (schema, name, template file, feed rule, every option) and one template. The two shipped posts share a template (a test keeps them identical) and differ by options and feed rule. To make your own, copy a folder, edit it and point `openchuck-cli regenerate --post` at it; no rebuild is needed. A new post should come with golden G-code files that the reader and replay checks cover. The Z1 conventions in `makera-z1/post.toml` are derived and unconfirmed until the air cut (OI-37); generated G-code is yours to verify before running (NFR-12).

Machine conventions (A-axis letter, direction, wrap, feed mode) live here and in machine profiles, never in the engine (GC-04).

`combine_rotary_runs` (decision 0506, accepted) writes a run of consecutive fed moves that turn A only, at the same X, Y and Z, the same way round and with the same feed, as one block, so the controller plans one rotation instead of one per step. Both built-in posts set it to `true`; a post that leaves the key out writes every step. Set it to `false` in a copied post to compare the two on a machine.

`safety_notice` (decision 0533) writes the NFR-12 notice as two comment lines after the generator line: the program has not been run on your machine, check it, simulate it and air cut it first. The wording is fixed in the post crate (`SAFETY_NOTICE`), not in the post. Both built-in posts set it to `true`; a post that leaves the key out writes no notice, as before. It needs `comments = true`, and a template that does not write it while it is on is refused, so the notice is never lost without a word. Generated G-code is yours to verify before you run it (NFR-12).

`max_line_length` (decision 0656) is the most characters a line may have. The Makera Z1 post sets 63: the Z1 firmware source keeps a line in a 64-byte queue item and cuts a longer one short without a warning (OI-933; from the source, not confirmed on the machine). The LinuxCNC post sets 255. A comment longer than the limit is wrapped at spaces onto more comment lines, so the Z1 writes the safety notice on four lines, word for word; any other line over the limit is a G-code check finding that stops the export. A post that leaves the key out is neither wrapped nor checked. `active_comment_prefixes` (issue #851, decision 9901, proposed; number provisional) lists the openings of comments the controller acts on instead of skipping. The LinuxCNC post lists LinuxCNC's fourteen (`MSG,`, `DEBUG,`, `PRINT,`, `LOG,`, `LOGOPEN,`, `LOGAPPEND,`, `LOGCLOSE`, `PY,`, `PYRUN,`, `PYRELOAD`, `ABORT,`, `PROBEOPEN`, `PROBECLOSE`, `RPY`, from its source); text from the project that would start such a comment, after spaces and in any case, and each line a wrapped comment starts, is written with `_` in front (`ACTIVE_COMMENT_GUARD`). The post's own header and footer are written as they are (a later line of one that is wrapped is marked). Each guarded text is reported in `PostOutput::guarded_comments` with its source (`CommentSource`), so the host warns the user. The Makera Z1 post lists none: its firmware acts on no comment (from its source). `coolant` (decision 0654): with `flood` or `mist` the template writes `M8` or `M7` after each spindle start and `M9` before the next tool change and before the footer; both built-in posts leave it `off`.
